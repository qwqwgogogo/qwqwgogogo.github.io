把自己的 agent 接上本地服务（ComfyUI、桌面自动化），通过 MCP 走。调通过程里四个坑都不是「功能不支持」，全是环境细节。

## 坑一：配置里写裸命令

```yaml
comfy-mcp:
  command: comfy-mcp
```

命令行里手敲 `comfy-mcp` 是能起来的，因为那个 `Scripts/` 目录在你终端的 PATH 里。但 agent 起子进程用的是一份自己的环境，PATH 里没有它 → 进程起不来，而且往往**没有像样的报错**，只显示连接失败。

改成绝对路径立刻就好：

```yaml
comfy-mcp:
  command: E:\\...\\venv\\Scripts\\comfy-mcp.exe
```

规则：**给 agent 写的 MCP 配置里，命令一律用绝对路径。** 让它去猜 PATH 没有任何好处。

## 坑二：端口这件事，三个来源三个答案

同一个 ComfyUI，我手上三个「权威说法」打架：

| 来源 | 说的端口 |
| --- | --- |
| 我整理的部署文档 | ComfyUI Desktop 默认 8000 |
| 它的 `cli_args.py` | `default=8188` |
| 一份旧运行日志 | `To see the GUI go to: http://127.0.0.1:8000` |

被旧日志带偏过一次：把 MCP 指到 8188，又改回 8000，还顺手把另一个服务挪到 8010。绕了一圈。

最后不引用任何文档，直接量：

```bash
netstat -ano | findstr LISTENING      # 谁真的在听
curl http://127.0.0.1:8188/system_stats
```

量出来是 **8188 上跑着 ComfyUI 0.40.0，8000 空闲，8010 根本没监听**（那个服务压根没自启，不是端口问题）。之前那条 8000 的日志是某个版本某次启动的残留。

规则：**端口、版本、路径这三类事实只能现场量，不能引用。** 我踩的这次，错的是文档、旧日志和我自己的记忆，只有 `netstat` 没说错。

## 坑三：装新包把依赖顶了

`pip install comfy-mcp` 顺手把 `mcp` 从 1.28.1 升到 2.x。结果 agent 侧的 MCP 客户端炸了：

```
CallToolResult has no attribute 'isError'
```

字段从驼峰变成下划线，典型的版本不兼容。当时打了个 `getattr(result, "is_error", ...)` 的兼容补丁能跑，但**每次更新 agent 都要重打一遍**——这种补丁不写进 README，下次更新必忘。

后来客户端升级、内部重构，那个补丁反而不需要了。所以「永久补丁」这个说法本身就该怀疑：能记清「什么时候需要它、什么时候可以扔」才是真省事的办法。

## 坑四：环境变量串味

从 agent 自己的 venv 里启动 ComfyUI，`PYTHONPATH` 会带过去，于是 ComfyUI 用的是 agent 那份 PIL——报出来的错和 PIL 本身没关系，很难查。

修法就一句：启动目标服务前清掉 `PYTHONPATH`。

## 一个顺带的收获

桌面自动化那个 MCP 到底怎么「看见」屏幕的？翻了它的源码：读的是 **Windows UI Automation / IAccessible2 无障碍树**，不是截图 + OCR。

这个区别很实际：能不能操作某个软件，取决于它有没有把控件信息暴露给系统无障碍接口，而不是图像识别准不准。所以下拉框、自绘界面的软件往往更难操作，而原生控件的反而顺利。

## 归纳

这四件事的共同点：**症状出现在连接层，原因在环境层。** 看到「连不上」就去改连接配置，是在错误的那一层打转。先确认进程在不在、用的是哪份环境、端口上到底是谁——三句话问完，问题一般就换了个更容易懂的样子。
