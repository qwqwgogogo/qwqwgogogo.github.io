OpenMAIC 是清华 THU-MAIC 开源的多智能体互动课堂（MIT，[THU-MAIC/OpenMAIC](https://github.com/THU-MAIC/OpenMAIC)），本地跑起来是 `pnpm dev` 起一个 Next.js，浏览器开 `localhost:3000`，数据存在一个 Docker 里的 Postgres 16。

生成过两个课件，隔了几天再打开，**列表是空的**。

## 第一反应是错的

「数据库崩了」「数据被删了」——这是脑子里冒出来的第一个假设，然后就开始想恢复方案。

停一下。这个假设是可以直接否证的，而且否证它的成本几乎为零。

## 实际排查

先看日志，里面有一行很关键的：

```
failed to connect to the docker API at
npipe:////./pipe/dockerDesktopLinuxEngine; check if the daemon is running
```

翻译成人话：**Docker Desktop 根本没开着。**

于是链条就通了：

```
Docker daemon 没跑
  → Postgres 容器没跑
    → 应用连不上数据库
      → 前端拿不到任何记录
        → 看起来像「数据没了」
```

同期还有一串后台进程 `exit code 127`（命令找不到），说明启动脚本本身也没稳定跑起来。这两个是同一类问题的两个表现：**依赖没起，被误报成数据没了。**

至于数据本身，Postgres 用的是 Docker 卷，容器停掉不会删卷。所以只要卷还在，把 daemon 和容器起回来，课件应该就在。

## 该用的顺序

凡是「本地服务的数据突然不见了」，按这个顺序查，前两步都是只读操作：

1. **应用进程在不在** —— `netstat -ano | findstr <端口>`；
2. **它依赖的东西在不在** —— Docker：`docker ps -a`；数据库：单独连一次；daemon 没起的话 `docker ps` 会直接把错误告诉你；
3. **最后才看数据文件/卷** —— 卷还在不在、时间戳和大小有没有变化。

走完这三步再谈恢复。**不要在只读检查之前做任何「看起来能修好」的写操作**——重装、`docker volume rm`、删库重建，这些都是不可逆的，而它们要解决的问题八成在第 1、2 步。

## 这条线没有圆满结局

诚实记录一下：这篇只写到「根因定位到 Docker daemon 没跑」。课件最后有没有回来，我的记录里没有确认过——那天的会话在中途断了，没有「起回来以后列表里有两个」的截图。

所以它不是一个「完美解决」的故事，是一个**排查顺序**的故事。

## 顺带：为什么把它换成本地模型

那几天正好在折腾用哪个模型驱动它。云端按 token 计费，试错阶段烧得快，于是把配置里的云端 provider 去掉，改成本地起的 OpenAI 兼容端口：只改 `base_url` 和模型名两行。

省的是 API 钱，代价是生成质量和速度——课堂是逐页生成的，本地模型本来就慢，页数一多等待时间很难看。这个交换值不值，取决于你是「天天用」还是「偶尔试」。

另外，把 key 交出去这件事我确实会犹豫：接云端模型时，我的提示词和生成的课件内容都会离开这台机器。试错阶段用本地更省心，不只是省钱的问题。
