有一次让 agent 干活，它回了一段很短的话：

> 我诚实说：**还没好**。我这轮一直卡在一个工具调用缺陷上——每次发 shell 命令时，参数外层都被我多包了一层 `arguments` 键，导致 `terminal` / `execute_code` 全部被拒绝执行（输出 `expected string, got NoneType`）。

前面几轮我看到的是它说「正在扫大文件」「准备下载」，然后是失败信息。我当时的判断是环境有问题：路径不对、网络被挡、磁盘不够。都不是。

## 症状长什么样

调用被拒收，报错是这样的：

```
Invalid command: expected string, got NoneType
No code provided
missing required field 'path'
```

关键在于**报错里没有一条是关于命令内容的**。没有「找不到文件」，没有「权限不足」，没有「网络超时」，全是「你该给我字符串，你给了 None」这类**参数校验**的错误。

真实原因：本该是 `{"command": "..."}` 的位置，被包成了 `{"arguments": {"command": "..."}}` 之类的形状，runtime 在顶层取不到 `command`，于是类型报错。命令一个字都没执行过。

这个形状错误是我这边（模型侧）的生成毛病，不是服务端 bug——所以它的表现是**间歇性的**。同一次会话里，它前面还有几条 `terminal` 真跑通了（一条自检、一次磁盘查询、一次目录列表），后面就全被拒。看着像「能力掉了」，其实是同一个通道在抖动。

## 为什么重试不解决问题

它自己那句总结我很认同：

> 这是我无法靠改文本来绕过的生成缺陷。

重试之所以无效，是因为**出错的位置在参数结构，不在文本内容**。同一个缺陷的下一轮采样，很可能还是同一个结构；就算侥幸通过一次，你也不知道它是真的好了还是碰巧。它当时试了八次以上，把上下文烧掉一大块，最后才停下来承认。

不过有一类绕法是真有用的：**换工具**。同一轮里 `search_files`、`write_file` 一直能跑，只有需要执行 shell 的那两条通道坏。所以「换个工具能不能过」是区分「整个会话废了」和「某条通道坏了」最快的判据。

后来它用这个判据推出了一个可行的绕法：既然 `write_file` 稳定，就把 shell 逻辑写成一个脚本文件落盘，再用**尽量少的** `terminal` 调用去驱动它，下载放后台跑（顺带绕开前台 600 秒超时）。这是把不可靠的通道用量降到最低，而不是指望它变可靠。

## 最该做的那件事：写交接单，开新会话

它最后给出的建议是这个，我认为是对的：

> 这个会话的 shell 管道坏了，硬修它我不争气（试了 8+ 次）。最靠谱的走法是开一个新会话，我带着这些已核实事实直接在能用的环境里执行。

于是它把已确认的事实——GPU、软件版本、端口、磁盘剩余、选定的方案和每个文件的大小——整理成一份执行交接单写进工作目录，**3402 字节，verified**。

注意那个 `verified`。同一段对话里，它前面还说过「文件我这次写不进去，但内容我一条不漏地给你」，几轮之后变成「已成功写入，3402 字节，verified」。两种说法都出现过，谁也没说错——中间那条通道确实恢复了。但从我这边的角度看，这意味着**它关于自身状态的句子不能直接采信**：落了盘的东西我去看一眼文件才算数，路径和字节数是能核对的。

事实清单单独落盘这件事本身很关键：新会话不用重新查一遍，也就不会在新环境里把同一批错误再犯一次。

## 我这边学到的三条

**一、看到类型层面的报错（None、missing required field、got object）就去怀疑调用形状，不要怀疑环境。** 环境问题的报错一定带业务语义：文件不存在、连不上、没权限。

**二、同会话里换一个工具试一次，成本极低，信息量很大。** 能区分「会话废了」「通道抖了」「权限不够」三种情况，而这三者的处理方式完全不同。

**三、重试烧的是上下文，而上下文烧掉之后它会开始忘。** 八次重试之后那份对话里塞满了失败信息，后面的判断质量必然下降。值得给 agent 立一条规矩：**同类错误连续三次没解决就停下汇报**，汇报要包括「已经试过什么」和「我现在怀疑什么」。承认「还没好」比第五次重试有用——这次它确实停下来了，但那句话出现在第八次之后。

第四条是给模型自己写的：别把「我打算做」写成「我做完了」。这类缺陷最坏的后果不是卡住，是**你以为它做完了**。
