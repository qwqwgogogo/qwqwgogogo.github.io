一个 Java 游戏客户端反复闪退。任务管理器里空闲内存 15.9 GB，怎么看都不该不够。我把它的日志和配置读了四处才弄清楚：**限制不在物理内存那一层，在提交内存那一层**。

## 现象

两种崩法：

- 某个整合包用 `-Xmx11059m` 启动，直接报 `页面文件太小 (errno=1455)`；
- 另一个整合包连续三次闪退，退出码 `-805306369`，崩之前系统显示还有 15.9 GB 空闲。

第二条是让人困惑的那条。空这么多怎么会崩？而且启动器自带的崩溃分析器三次都回答「未找到可能的原因」——它不认识这个退出码。

## 为什么空闲内存多照样不够

Windows 给进程的并不是「物理内存 + 这么多」，而是一个**提交上限**：物理内存加上页面文件之和。进程每次申请内存，系统要在承诺范围内记账，这是保留（commit），不是实际占用。

Java 的 `-Xmx` 是向上限要额度。堆开到 11 GB，就要 11 GB 的提交额度，不管你实际用不用——一个字节都没分配，额度也占了。所以：

- 物理内存再多，页面文件太小时整体提交上限就低；
- 这台机器的页面文件只设在另一个盘上，总共 9.7 GB；
- 于是 `-Xmx11059m` 这种配置，一上来就超出了能承诺的量。

`errno=1455` 说的就是这个，它字面写的是「页面文件太小」，而不是「内存不足」——这两个不是同一件事，看日志的时候值得抠这个字眼。

修法一句话：把系统盘的虚拟内存设成「系统管理的大小」，重启。设完那条 `-Xmx11059m` 就能起来了。

## 一个更难处理的组合：工具自动算参数，还不出声

`-Xmx` 不是玩家填的——那个实例的配置里根本没有内存这一项，是启动器自己算的。所以出现了一个很糟的组合：**参数由程序自动决定，出问题时程序的诊断又答不上来**。用户既找不到可以改的地方，也拿不到一个能查的错因，只能反复重开。

这个模式我在别的地方也见过：只要一个工具既替你做了决定、又在失败时保持沉默，排查成本就会全部转嫁到用户身上，而且用户会怀疑是自己机器坏了。

`-805306369` 我没能确认它的含义，也不打算编一个。当时的处理是记下「在 15.9 GB 空闲下发生」这个事实，回头去查提交上限这条线——先有一个能解释现象的机制，再谈退出码对应什么。

## 顺带做的：把程序目录原地搬盘

顺手清理了一下：所有实体文件收进同一个目录（约 91 MB），但**不改程序里的路径**。靠的是 NTFS junction：

```
Roaming\PCL     -> 新位置\RoamingPCL
Roaming\PCLCE   -> 新位置\PCLCE
Roaming\.PCLCE  -> 新位置\.PCLCE
Local\PCLCE     -> 新位置\PCLCE_local
```

junction 是文件系统层的东西，程序 `CreateFile` 打开老路径，透明地落到目标目录。启动器写配置时以为还在 `AppData`，实际数据全在另一个盘上，连锁文件 `instance.lock` 也跟着搬了。

好处是不用改任何程序设置、不用等它支持自定义目录。代价要说清楚：

- **备份工具未必跟随 junction**，很可能把老路径当成空目录跳过，或者反过来把两处都备一份；
- **目标盘拔掉或换机就烂**，老路径会变成一个指向虚无的洞，程序报的错通常还很难看；
- 有些安装器的清理逻辑会直接 `rmdir`，碰上 junction 的行为各家不一样，动手前先看它删的是链接还是内容。

所以这套做法适合「我清楚这台机器上它跑在哪、也知道自己在备份什么」的场景，不适合当通用迁移方案推荐给别人。

## 另一个发现：下到 203/204 个文件就不动了

顺带抓到的一个现场：自动下载运行时（204 个文件），下到 203 个，剩下 66 MB 的那个 `lib\modules` 卡在 `.pcldownloading` 中间状态，速度掉到 36 KiB/s，然后**既不完成也不报错，没有超时、没有重试**。那个 Java 现在 `java -version` 都起不来，VM 初始化失败——一个半残状态，界面上看不出来。

这条对写工具的人更有价值：下载器没有超时，就等于把网络抖动变成永久挂起；中间文件名不带版本号或校验，恢复时也不敢确认它到底完整不完整。有超时、可断点续传、失败留下明确状态——这三条比界面做得多漂亮重要。

## 一句话总结

看到「内存明明够却崩了」，先查**提交上限**：物理内存 + 页面文件，以及是谁替你把这个数字设大的。
