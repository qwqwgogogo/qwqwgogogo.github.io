## GPU 是怎么长出来的

许多微处理器要连接 PC 或者工作站上的图形显示设备，用于图形显示的处理时间在整机里占比越来越大。当微处理器设计中可用的晶体管数量按摩尔定律继续增长时，把这部分晶体管预算拿去提高图形处理能力就变得很必要。

另一股推力来自市场。计算机游戏产业包括 PC 和专用游戏终端（例如 Sony PlayStation），快速增长的游戏市场促使许多公司加大快速图形硬件的研发，形成正反馈，使图形处理能力的增长超过了主流微处理器的通用处理能力。由于图形和游戏开发与微处理器开发的目标不同，图形处理形成了自己的一套处理风格和术语。随着图形处理器地位上升，它被命名为图形处理单元（写作 GPU），以区别于 CPU。

## 差异一：设计目标和任务类型

CPU 设计用来执行广泛的计算任务，包括操作系统管理、应用程序逻辑、文件处理等，它是系统的「大脑」，负责协调和控制计算机的整体操作。GPU 最初设计用于处理图形渲染任务，例如视频游戏和三维图形渲染；随着技术发展，它也被用于通用计算（写作 GPGPU），执行深度学习、科学计算这类大规模并行计算任务。

这一条决定了后面所有取舍：一个要为「什么都能算」优化，一个要为「同一件事算很多次」优化。

## 差异二：处理能力与任务规模

CPU 擅长处理复杂的逻辑和顺序执行的任务，能够处理从几 KB 到几 TB 的数据量，但处理大规模并行任务时效率较低。GPU 拥有大量处理单元，例如 CUDA 核心和流处理器，能够同时处理成百上千个简单的并行任务，非常适合处理几百 MB 到 GB 量级的大规模数据集。反过来，对非并行或者逻辑复杂的任务，GPU 的效率可能不如 CPU。

答题时不要只写「GPU 核多」。要写清任务形态：GPU 吃的是大量简单任务，CPU 吃的是少量复杂任务。

## 差异三：内存架构

CPU 通常配备大容量的内存（RAM），从几 GB 到几 TB 不等，以支持广泛的计算任务，并且依赖多级缓存（L1、L2、L3 等）来减少访问主存的延迟。GPU 的内存容量相对较小，通常几 GB，但内存带宽非常高，专为并行处理设计。关键差别在于隐藏延迟的手段：GPU 不依赖多级缓存来隐藏内存访问延迟，而是靠硬件多线程和大量并行处理器来把它藏起来——这条线跟前面硬件多线程那一节直接接上。

## 差异四：并行处理能力

现代 CPU 也支持多线程和多核处理，但并行处理能力相对有限，主要用于处理复杂的逻辑和顺序任务。GPU 的并行处理能力极强，拥有成百上千个处理单元，可以同时执行大量简单的并行任务，因而在大规模并行计算任务上非常高效。

## 差异五：协处理器角色

在一个同时具有 GPU 和 CPU 的系统中，GPU 通常作为协处理器存在，与 CPU 协同工作。CPU 负责处理逻辑复杂或者顺序性强的任务，GPU 专注于大规模并行计算任务。这种分工可以显著提高系统的整体性能。也就是说，把 GPU 看成「更快的 CPU」是错的，它是挂在 CPU 旁边的专用算力，主控权仍在 CPU 手里。

## CUDA：绕开图形 API 直接写 GPU

GPU 最初只是为少数应用程序设计的，但一些程序员渴望利用 GPU 内部潜在的高性能，在厌倦了用图形 API 语言描述问题之后，开发了类 C 的编程语言，用于在 GPU 上直接编程。NVIDIA 的 CUDA 便是其中的典型：它让程序员能编写直接在 GPU 运行的 C 程序，不过仍存在一定限制。CUDA 的引入极大扩展了 GPU 的应用范围，使它不再局限于图形渲染，而能够处理各种需要大规模并行计算的任务。

## CUDA 的三层抽象

**CUDA 线程**：GPU 上的所有并行计算单元都被抽象成 CUDA 线程，它是 CUDA 编程中最基本的并行执行单元。开发者编写的是 CUDA 内核，也就是运行在 GPU 上的函数；这个函数可以并行地执行多次，每一次执行就是一个 CUDA 线程。这些线程可以独立访问 GPU 的内存，并执行相同的指令序列（SIMD 形态），或者根据不同条件执行不同的指令序列（MIMD 形态）。

**线程块**：为了更有效地管理和调度线程，CUDA 把它们组织成线程块。每个线程块通常包含几十到几百个线程，具体数量取决于 GPU 的架构和配置。常见的配置是以 32 个线程为一组一起执行，因为这样能优化内存访问和指令分发。同一个线程块里的线程可以协同执行，并共享某些资源。

**流多处理器**：GPU 内部包含多个流多处理器（写作 SM），它们是执行线程块的硬件单元。每个 SM 可以并行处理多个线程块，从而进一步增加并行度；不同型号的 GPU 包含的 SM 数量不同，从几个到几十个不等。

再往上还有一层：线程块被进一步组织成网格，网格中的每个线程块可以独立执行，GPU 可以同时执行多个线程块，每个线程块中的线程也并行执行。抽象层级和硬件单元的对应关系是这道题的核心——线程块要被派发到 SM 上执行，所以一个线程块不能被拆到两个 SM 上去共享私有资源。

**资源管理**：CUDA 提供不同的内存区域来管理和优化数据的存储与访问，包括全局内存、共享内存、常量内存和寄存器。写程序时的取舍基本就是这套层级：全局内存所有线程都能访问、容量大但慢；共享内存限定在线程块内部、用来做块内协作；常量内存适合广播不变的输入；寄存器最快但只属于单个线程。

## 为什么线程要三十多个一组

线程块不是随便切的，硬件按更小的粒度发射指令。所谓 32 个线程为一组一起执行，指的是这 32 个线程共用一套控制逻辑，同一拍发同一条指令，各自带着自己的数据地址。这样做的收益有两处：指令分发只需要一份，控制开销被摊薄到 32 份数据上；访存请求可以合并，相邻线程访问连续地址时能一次取回一整块，这就是所谓优化内存访问。

代价也立刻显出来。分支发散是它的老毛病：组里一半线程要走 if、另一半要走 else 时，两条路径只能串行执行，不走这条路的那些线程这一拍被空置，等效吞吐随之下降。这和 SIMD 机处理 case 或 switch 时性能只剩 1/n 是同一件事，只是换了层皮。所以写 GPU 程序时，把分支按数据划分到不同线程块里，比在一个块里各走各的要划算。

## 数据是怎么在 CPU 与 GPU 之间走的

GPU 作为协处理器，不接管主存地址空间：它有自己的显存，全局内存就挂在上面。一次典型计算的路径是：CPU 准备输入，把数据搬到 GPU 的显存，启动内核，让成千上万个 CUDA 线程并行算完，再把结果搬回来。搬运这一段靠的是直接存储器访问式的批量传输，不占 CPU 逐字读写。

由此得到一个很实际的判据：数据量小的任务不适宜搬到 GPU。搬运开销是固定的，计算量太小就摊不平，算得再快也没用。真正值得用 GPU 的任务通常同时满足几条：数据规模在几百 MB 到 GB 量级、同一操作重复打在大量同构元素上、分支少而访存规则、可以一次批量喂进去再一次性取结果。

## 什么任务落在 CPU、什么任务落在 GPU

按前面五维差异倒推一遍就很清楚。操作系统管理、应用程序逻辑、文件处理这类控制密集又顺序的活留在 CPU；图形渲染、深度学习的矩阵乘、科学计算里大规模同构数据的逐元素操作落到 GPU。逻辑复杂、依赖多、分支多、数据量又小的任务，交给 GPU 反而更慢，因为它的单线程性能并不占优，靠的是并行度取胜。

隐藏延迟的思路差异也在这里：CPU 用大缓存提前把数据备好，GPU 用大量可切换的线程填住等待的时间。前者靠存储器层次，后者靠线程级并行，这是两条完全不同的工程路线。

## 内核这个词指什么

CUDA 程序里跑在 GPU 上的那个函数就叫内核。它被写成一次执行的形状，却被并行地启动很多次，每一次执行就是一个 CUDA 线程，线程编号决定它处理哪一份数据。程序的其他部分仍在 CPU 上：分配显存、拷贝输入、设置线程块与网格的规模、启动内核、回收结果。理解成「CPU 编排、GPU 干活」最不容易出错，也正好对应协处理器那一维差异。

## 三个容易答偏的地方

一是把 GPU 的高吞吐归因于高主频。它的单核并不快，靠的是数量与并行发射，以及用硬件多线程而非大缓存来掩盖访存延迟。

二是把内存带宽与内存容量混说。GPU 的优势是带宽高，容量通常反而较小；CPU 平台的内存容量可以很大并靠多级缓存降低延迟，两者的优化方向不同。

三是把 CUDA 说成一种硬件。它是编程模型和工具链，靠类 C 语言把 GPU 的并行能力暴露出来；线程、线程块、网格是软件概念，SM 才是落在硅片上的执行单元。
