## 一句话

上一节留下的账很难看：页表本身在主存里，于是「读一个数据」变成了「先读它的地址映射，再读数据」，访存次数直接翻倍。TLB 就是冲着这笔账来的——它把层次结构的思想再用一次，只不过缓存的不是数据，而是页表项。

## 为什么非要有快表

一次没有快表辅助的页式地址转换，要走这么长一条路：CPU 给出逻辑地址，MMU 取出页号，用页号去主存里定位页表项，把页表项读回来，判断有效位，取出物理块号，拼上页内偏移得到物理地址，再拿这个物理地址去主存取真正的数据。两次主存访问是下限，页表分级之后还会更多。

把两次访问压回一次的办法只有一个：让最常见的映射结果不要总去主存里查。页表项是会被反复使用的——进程在一段时间里活跃的就那么几页，同一页里的几千个地址都共用同一条页表项。这正是时间局部性，而时间局部性一向是交给 Cache 处理的。

于是硬件里加了一小组专用存储，缓存最近用过的虚拟页到物理块的映射，这就是快表，英文写作 TLB。

快表的名字很直白：它不存数据，只存映射，专门用来把地址转换那一次额外访存省掉。

## TLB 里存什么

TLB 的每一项本质上是一条被搬上来的页表项，常见字段是：

| 字段 | 作用 |
| --- | --- |
| 页号（标记） | 和逻辑地址高位比较，判断命中 |
| 物理块号 | 命中后直接拿去拼物理地址 |
| 有效位 | 这一项还作不作数 |
| 访问位、地址改变位 | 供置换和写回参考 |
| 权限位 | 读写执行限制，越权照样中断 |
| 进程标识（ASID 之类） | 区分不同进程的同一页号 |

注意最后一项：页号只在单个进程的地址空间里有意义，两个进程都有页号 7，物理块却毫不相干。

## 命中与缺失

**命中**：逻辑地址的页号拿来和 TLB 里的项比较，匹配上且有效位为 1，就立刻得到物理块号，偏移照搬，然后一次访存取数据。整条路只走了一次主存访问，地址转换在硬件里当场完成，程序完全无感。

**缺失**：TLB 里没有这一项，只能回到主存去读页表，读出块号后按物理地址取数据；如果这一页确实驻留在主存中，还要顺手把这条映射装进 TLB，供下一次用。装不进就按某种置换策略挤掉一条旧项。

**页也不在主存**：这时候 TLB 缺失只是表象，真正要处理的是缺页，交由操作系统，代价几个数量级往上跳。

## 组织方式：为什么小表才敢做全相联

TLB 通常只有几十到几百项——一条项能覆盖 4KB，1024 项就意味着 4MB 的地址范围被盯住了，容量需求天生比数据 Cache 小得多。

规模小，才用得起最贵的组织方式：全相联。逻辑地址里的页号不做任何索引切分，而是和表里每一项的页号同时比较，一次就出结果。代价是每一项都要一套并行比较电路，实现上往往直接依赖内容寻址存储，功耗和面积都很吃紧，所以容量做不大。

规模稍大一些就改成分组的方式：拿页号的低位当组索引，组内再并行比较。这时地址转换变成「索引 + 组内比标记」，和 Cache 的组相联完全同构；也正因为同构，TLB 的命中率、缺失惩罚、置换策略这些概念可以直接从数据 Cache 那一套搬过来。

现代处理器常把 TLB 也做成两级：小容量、极快的第一级挂在每个核上，容量较大的第二级由多个核共享。L1 未命中先查 L2，都未命中才去读主存页表。

## 上下文切换：整表作废太贵

上下文切换是快表设计里最容易忽略的一处代价。

进程切换时最容易想当然的做法是「把 TLB 全清了重来」，因为所有映射都换了主人。问题是清表之后每一页都要靠页表缺失重新装一遍，这段时间访存代价直接翻倍，而且切换越频繁惩罚越重。

解决办法是给每一项打上进程标识：表项里存着它属于哪个地址空间，比较时不只比页号，还要比这个标识。这样上下文切换不需要清表，两个进程的映射可以共存于一张表里，只要标识不同就不会错认——只有真正没有余量时才按置换策略逐条淘汰。

同理，页表内容被修改时必须让相关的 TLB 项失效，否则会出现「页表说这一页已经搬走了，快表还把它当成在主存里」的陈旧映射。失效可以整表清，也可以按标识只清某个进程的那些项，后者代价小得多。

## 有效访问时间

有效访问时间是把快表收益量化下来的唯一口径。设主存一次访问 100 ns，TLB 命中率 98%，命中时只需 1 次访存，缺失时要先读页表再读数据、按 2 次访存计（TLB 自身的比较与更新开销忽略）：

```
EAT = 0.98 × 100 + 0.02 × 200 = 102 ns
```

对照没有快表时的 200 ns，这个只有 2% 提升率的表把平均代价压掉了近一半。数字本身不重要，重要的是式子结构：**命中率越高，缺失那一项的权重就越小**，这也是为什么 TLB 哪怕很小也值得存在。

把缺页也算进来时还要再加一层：缺页要转入操作系统、访问磁盘，代价在毫秒量级，所以真正决定性能的是「每多少次访存发生一次缺页」，而不是快表命中率。

## 大页：用粒度换命中率

既然一条 TLB 项能覆盖一整页，那么把页做大，同样大小的表就能盯住更大的地址范围。

大页把页面从 4KB 提到 2MB 甚至 1GB，数据库这类工作集巨大、访问又相对均匀的负载受益明显：TLB 覆盖率成倍上升，页表本身也短了一大截。

代价是内部碎片变大，只用了几十字节的页也要占满整块；而且换入换出的粒度变大，缺页一次要搬走几兆数据，稀疏访问的负载反而吃亏。

所以现代系统是混合粒度：同一张表里同时允许 4KB 和 2MB 两种页，项里带上页大小标记，MMU 按各自的方式切分页号和偏移。

## TLB 缺失由谁处理

快表未命中之后谁来补这一项，有两种做法，代价差别不小。

硬件管理的方式由 MMU 自动去走页表、填快表，流水线只需短暂停顿，代价是多级页表时每查一级都要一次访存，硬件状态机也得把整条 walk 走完。软件管理的方式则在未命中时转入异常处理程序，由操作系统负责找项、写回快表，硬件简单了，代价是多一次异常进出的开销。

判断哪种划算的口径很朴素：页表级数浅、访问密集，硬件方式更合适；表很深、策略要灵活（比如按进程定制置换），软件方式更好写。

共享映射是快表另一个容易出错的场景。多个进程映射同一段物理页（共享库、共享内存段）时，它们的页号各不相同，但块号指向同一处。这些项在快表里是彼此独立的条目，回收其中一页时要把所有相关项一起失效，否则会出现「一个进程已经看不到、另一个进程还在读写」的不一致。

## 一张表能盯住多大范围

这是快表题里最常见的一问，算法只有一步：**覆盖范围 = 项数 × 每项覆盖的页面大小**。

64 项的快表，页面 4KB，能盯住 `64 × 4KB = 256KB` 的地址范围；同样 64 项换成 2MB 的大页，覆盖范围一下子变成 `128MB`，两倍之差全靠粒度，不靠项数。

反过来，如果题目给出「一个进程的工作集是 8MB，快表要全部盯住」，那么需要的项数就是 `8MB / 4KB = 2048` 项。这个数字一下来就能明白为什么大页对内存密集型负载那么重要——不是表不够快，是表不够宽。

## TLB 与数据 Cache 的区别

两者都是靠局部性吃饭的小容量高速缓冲，但管的对象完全不同，混了就答不到点上：

| | TLB | 数据 Cache |
| --- | --- | --- |
| 缓存内容 | 页表项，即地址映射 | 数据本身 |
| 解决的问题 | 转换要额外访存 | 主存比 CPU 慢 |
| 单位 | 页，4KB 起 | 块，几十到上百字节 |
| 位置 | 在 MMU 里，访存之前 | 在 CPU 与主存之间 |
| 缺失后果 | 多读一次页表 | 多读一次主存或下一级 Cache |
| 是否影响物理地址正确性 | 是 | 否 |

一次访存在硬件里的次序是：先 TLB 做逻辑到物理的转换，再用物理地址去查数据 Cache。两者是串联的两道关卡，不是同一个东西的两种叫法。也正因如此，Cache 里放的是物理地址还是虚拟地址，是个真实存在的设计选择——用虚拟地址索引可以早一点开始比对、缩短命中时间，但切换进程时表里就可能出现别的进程的项，要靠地址空间标记来区分。

## 一句总结

TLB 存在的意义只有一句话：它让「查映射」这件事不再需要访问主存，于是虚拟存储器带来的那笔翻倍代价被基本抹平了。表很小、很贵、全相联、按进程打标记，这四个特征全都从「它缓存的是页表项」这一句推出来。
