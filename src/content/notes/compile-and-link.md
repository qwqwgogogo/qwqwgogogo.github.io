## 一句话

**编译管「一个文件变成一堆带符号的机器码」，链接管「把很多堆符号拼成一个程序，并给每个符号定下地址」**——搞混这两步，就解释不了为什么重复定义要到链接期才报错。

## 四步

| 步骤 | 输入 → 输出 | 干什么 |
| --- | --- | --- |
| 预处理 | `.c` → `.i` | 展开 `#include`、`#define` |
| 编译 | `.i` → `.s` | 高级语言翻译成汇编 |
| 汇编 | `.s` → `.o` / `.obj` | 生成目标文件，里面是机器码加一张符号表 |
| 链接 | 多个目标文件 → 可执行文件 | 汇总符号表，确定每个符号的地址 |

从源码走到可执行文件一共经过四个阶段，最先动手的是预处理，它只负责把包含的文件和宏展开，此时还没有任何翻译发生。汇编阶段结束后，每份源文件都对应一个目标文件，目标文件里既有机器码也有一张待填的符号表。

关键的一条：一个 `.c` 生成一个目标文件。这两个过程是独立的，所以 `foo.c` 里调用一个根本没实现的函数，编译阶段照样通过——编译器只看这一份文件，它认为符号存在就行，找不到是链接器的事。

链接器除了打包所有目标文件，还要拉进标准 C 库和操作系统那套初始化代码，`main` 之前跑的那些东西就是它塞进去的。

## 符号默认是公共的

C 语言里写一个函数，它的符号默认对整个程序有效。于是两个 `.c` 里有同名函数，链接器汇总符号表时发现同一个名字有两个定义，直接报重复定义。

规矩是：

- 对外提供的接口，在头文件里**声明**，在某个 `.c` 里**定义**一次；
- 只在当前文件里用的辅助函数，统一加 `static`。

`static` 在这里的作用不是「变量活得久」，而是**把符号关进这一个编译单元**——链接器压根看不见它，也就不会撞名。同一个文件里两个函数都叫 `enlarge`，只要都是 `static`，互不干扰。

头文件里放的就是声明：函数体一旦写进头文件，每个包含它的 `.c` 都会生成一份定义，链接期立刻重复。

## 预处理还做哪两件事

除了把包含的文件原样搬进来，预处理还负责宏替换和条件编译。宏替换是纯粹的文本替换，不做类型检查，也不理解语法，这一点是许多诡异错误的来源；条件编译决定哪几段代码在展开后仍然存在，跨平台代码常用它来隔离不同系统的接口调用。

头文件会被多个源文件重复包含，重复展开的后果是同一个符号出现多份定义。传统的处理办法是在头文件首尾加一对条件编译保护，保证它在一个编译单元里只展开一次；另一种办法是只把真正需要的声明放进去，把实现细节留在源文件里，这同时也是接口设计的问题。

## 目标文件里到底有什么

一份目标文件不是纯机器码，它至少包含三样东西：分好段的机器码和数据（代码、已初始化数据、未初始化数据各归各段）、一张符号表（记录本文件定义了哪些符号、又引用了哪些外部符号）、一张重定位表（记录哪些位置的数值要等链接时才能填）。

符号表里区分得很清楚：本文件里定义了并给出了地址的，属于「已解决」；只有引用没有定义的，属于「未解决」，等着链接器去别处找。编译阶段之所以对未实现的调用一声不吭，正是因为目标文件允许携带未解决符号，这是设计而非疏漏。

## 链接器做的三件事

第一步是符号解析：把所有目标文件的符号表汇总，给每个引用找到唯一定义。同一个名字在两份目标文件里都有强定义，就是重复定义错误；某个引用在所有目标文件和库里都找不到，就是未定义引用错误。

第二步是地址分配与重定位：把各文件的同类段合并，给每个符号定下最终地址，再回头按重定位表把那些待填的位置逐个改写。第三步是拉入库：标准 C 库和运行期初始化代码在这一步被接进来，`main` 之前跑的那些准备工作就是它们提供的。

静态库在链接时被取出一部分复制进可执行文件，动态库只留下一个引用，运行期才由加载器映射进来。两种做法的取舍很直白：静态链接出来的文件更大但自带依赖，动态链接出来的文件小却要求运行环境里那份库存在。

## 编译单元这个词解决什么

一份源文件加上它预处理时展开进来的所有头文件，构成一个编译单元，也对应一个目标文件。这个概念的意义在于解释可见性：编译器做判断时只看这一个单元，跨单元的符号它一概不认识，因此「编译期检查」能查的只有语法和类型，「这个函数到底存不存在」这类问题必须留给链接器。

多文件工程的组织习惯也是从这里推出来的：一个模块一对文件，对外能力写在头文件里，实现细节留在源文件里，头文件之间不要互相绕圈包含。依赖方向越清楚，改动引起的重新编译范围越小，因为每个包含者都是一个独立的编译单元。

## 多文件编程到底解决什么

一个源文件写到几百行之后，问题不再是语法而是管理：改一处就要重新读一遍全部，别人无法只拿走其中一块，同一个功能在不同项目里重复出现。多文件编程的做法是把程序按功能切成若干编译单元，每个单元单独编译成自己的目标文件，最后由链接器拼成一个可执行文件。

这样切分之后，跨文件的引用必须先申明再使用：调用方所在的那个编译单元里，被调用者的名字必须先有一个声明，编译器才认得它。声明从哪里来，就是头文件——把接口集中写在一个文件里，谁要用谁包含，这也是「接口与实现分离」在 C 语言里唯一可行的落地方式。

## 头文件的两种包含方式

尖括号和双引号的差别在查找顺序上。尖括号按编译器预设的搜索路径去找，通常用于标准库和第三方库；双引号先在当前源文件所在目录找，找不到再走预设路径，通常用于自己项目的头文件。写反了不会报错，只会让人困惑为什么同一份头文件被展开成了不同版本。

包含是纯文本替换，展开后的内容仍然只属于这一个编译单元。因此头文件里出现定义就要格外小心：常量定义、内联实现、静态变量是可以的，普通函数和全局变量的定义则会随每个包含者生成一份符号，链接期一定撞车。

## 四步在命令行上长什么样

同一条流水线可以用不同参数停在任意一步：只要展开结果就停在预处理，只要汇编文本就停在编译，只要目标文件就停在汇编，全部走完才得到可执行文件。能停在中间这一步，价值在于定位问题——宏没有展开、类型转换被吃掉、段错误来自哪个符号，都能在中间产物里直接看出来，不必等到运行崩溃再猜。

调试信息是另外一件事：带调试选项编译时，编译器会在目标文件里多塞一张行号与变量名的对照表，链接器把它一起带走，调试器读的就是这张表。表本身不影响程序运行，去掉之后机器码一模一样，这也是为什么发布版本通常不带它。

## 工程管理器解决的是另一件事

一个目录里躺着几十个 `.c`，但构建目标 A 只需要其中几个，构建目标 B 需要另外几个。**工程管理器（IDE 里那个「项目」）管的就是「哪个目标由哪些 `.c` 组成」**，跟编译器无关。

`cmake` 的卖点是跨平台：解析同一份配置文件，为当前系统生成对应的工程管理文件——Mac 上出 Xcode 工程，Linux 上出 Makefile，Windows 上出 `.sln`。写一份规则，三个平台都能构建，代价是多一层生成步骤。

编辑器、编译器、调试器是三个独立的东西：`clion` 是 IDE，三样都带；`vscode` 和 `vim` 本质是编辑器，编译和调试要自己接。搞清楚这三层，才知道报错到底是谁抛的。

## 开发环境怎么配

课件对编译器版本没有特殊要求，为了照顾不同机器的配置情况，以 GNU 下的 gcc 为主：Windows 用 win11 配 gcc-13.2.0-mingw，另带 clangd 和 cmake；Linux 用 Ubuntu 22.04 或 24.04 自带的 gcc；Mac 是 ARM 体系的 M1，用 clang 14.0.3。

IDE 一侧的清单是 Clion（配套 cmake）、Visual Studio、VSCode、DevC++、CodeBlock。选哪一个都不影响前面那条流水线，变的只是谁替你敲那四行命令。

## 阅读材料的用法

学校发的教材以程序语法为目的，用法是遇到语法错误时去看例子、按需翻阅，配合的四本书是《C Primer》《C 和指针》《C 陷阱与缺陷》和《程序员的自我修养——链接、装载与库》。

学习路线切成四段，各段的目标不一样：基础篇 5.1 之前与进阶篇 3.1 之前属于程序语法基础；进阶篇 1.1 到 1.5 以了解为主；基础篇第 5、6 章加上进阶篇第 3 章和指针面试题，讲的是 C 语言内存思想与指针的理解；剩下的部分属于 C 语言函数思想，对设计项目和工程化管理有意义。前面那本讲链接与装载的书，正好落在最后这一段。

## 对照着背

| | 报错发生在 | 典型信息 |
| --- | --- | --- |
| 语法写错 | 编译 | `expected ';' before ...` |
| 声明了没定义 | 链接 | `undefined reference to ...` |
| 定义了两次 | 链接 | `multiple definition of ...` |
| 头文件找不到 | 预处理 | `No such file or directory` |

| 加 `static` | 效果 |
| --- | --- |
| 修饰函数 | 符号只在本 `.c` 可见，避免链接撞名 |
| 修饰局部变量 | 变量活到进程结束，但作用域不变 |
| 修饰全局变量 | 这个全局只在本文件可见 |
