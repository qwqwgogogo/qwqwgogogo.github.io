## 一句话

**编译管「一个文件变成一堆带符号的机器码」，链接管「把很多堆符号拼成一个程序，并给每个符号定下地址」**——搞混这两步，就解释不了为什么重复定义要到链接期才报错。

## 四步

| 步骤 | 输入 → 输出 | 干什么 |
| --- | --- | --- |
| 预处理 | `.c` → `.i` | 展开 `#include`、`#define` |
| 编译 | `.i` → `.s` | 高级语言翻译成汇编 |
| 汇编 | `.s` → `.o` / `.obj` | 生成目标文件，里面是机器码加一张**符号表** |
| 链接 | 多个目标文件 → 可执行文件 | 汇总符号表，确定每个符号的地址 |

关键的一条：**一个 `.c` 生成一个目标文件**。这两个过程是独立的，所以 `foo.c` 里调用一个根本没实现的函数，编译阶段照样通过——编译器只看这一份文件，它认为符号存在就行，找不到是链接器的事。

链接器除了打包所有目标文件，还要拉进标准 C 库和操作系统那套初始化代码，`main` 之前跑的那些东西就是它塞进去的。

## 符号默认是公共的

C 语言里写一个函数，它的符号默认对整个程序有效。于是两个 `.c` 里有同名函数，链接器汇总符号表时发现同一个名字有两个定义，直接报重复定义。

规矩是：

- 对外提供的接口，在 `.h` 里**声明**，在某个 `.c` 里**定义**一次；
- 只在当前文件里用的辅助函数，统一加 `static`。

`static` 在这里的作用不是「变量活得久」，而是**把符号关进这一个编译单元**——链接器压根看不见它，也就不会撞名。同一个文件里两个函数都叫 `enlarge`，只要都是 `static`，互不干扰。

头文件里放的就是声明：函数体一旦写进头文件，每个包含它的 `.c` 都会生成一份定义，链接期立刻重复。

## 工程管理器解决的是另一件事

一个目录里躺着几十个 `.c`，但构建目标 A 只需要其中几个，构建目标 B 需要另外几个。**工程管理器（IDE 里那个「项目」）管的就是「哪个目标由哪些 `.c` 组成」**，跟编译器无关。

`cmake` 的卖点是跨平台：解析同一份配置文件，为当前系统生成对应的工程管理文件——Mac 上出 Xcode 工程，Linux 上出 Makefile，Windows 上出 `.sln`。写一份规则，三个平台都能构建，代价是多一层生成步骤。

编辑器、编译器、调试器是三个独立的东西：`clion` 是 IDE，三样都带；`vscode` 和 `vim` 本质是编辑器，编译和调试要自己接。搞清楚这三层，才知道报错到底是谁抛的。

## 对照着背

| | 报错发生在 | 典型信息 |
| --- | --- | --- |
| 语法写错 | 编译 | `expected ';' before ...` |
| 声明了没定义 | 链接 | `undefined reference to ...` |
| 定义了两次 | 链接 | `multiple definition of ...` |
| 头文件找不到 | 预处理 | `No such file or directory` |

| 加 `static` | 效果 |
| --- | --- |
| 修饰函数 | 符号只在本 `.c` 可见，避免链接撞名 |
| 修饰局部变量 | 变量活到进程结束，但作用域不变 |
| 修饰全局变量 | 这个全局只在本文件可见 |
